# How mature distributed DBs handle graceful scale-down (ownership handoff)

Research survey for the shale Option B graceful-leave convergence problem. 24 sources, adversarially verified.

## Summary

Mature distributed databases keep moving keys available during a graceful scale-down by making the OLD and NEW owners overlap on the routing path for the duration of the handoff, and by ordering the transition so the leaving node never exits a replica set before the new owner has the data. Two architectural families exist: (1) the consistent-hash / gossip family (Cassandra, ScyllaDB pre-Raft, Riak/Dynamo) uses PENDING RANGES / pending_endpoints, where the coordinator dual-writes to current+pending owners (writes always go to all replicas; CL only governs ack count) and the leaving node keeps serving (stays in read+write sets) until it finishes streaming its data to the new owner; (2) the per-range-consensus family (CockroachDB, TiKV/PD, etcd/Consul) sidesteps ambiguous ownership entirely via Raft membership changes - add the new replica as a learner, snapshot/catch it up, promote to voter, transfer the lease/leader, then remove the old replica, so a single linearizable leaseholder/leader always exists. The gossip-lag ambiguity the question targets is exactly the failure that ScyllaDB's ring_delay (30s) wait, Cassandra's CEP-21 epoch'd metadata log, and ScyllaDB's topology-version fencing were each built to eliminate. For a consistent-hash + object-storage + gossip R=2 KV store, the smallest robust fix is to adopt Cassandra-style pending ranges: dual-write to current+pending owners and read from their union during a transition, gated so the leaving node stays in both sets until the new owner has mounted the shared bytes - which (because data is in shared object storage) makes "streaming" a near-zero-cost mount rather than a multi-second copy.

## Findings

### 1. [high] The canonical gossip/consistent-hash fix is Cassandra's PENDING RANGES: during a topology change the coordinator adds the node gaining a range to the set of write/CAS destinations IN ADDITION to the current owners, so the new owner receives every write while ownership moves. Writes in Cassandra always go to ALL replicas regardless of consistency level (CL only controls how many acks the coordinator waits for), and when pending ranges exist the required-ack count (blockFor) is raised to cover both natural and pending endpoints, so a read quorum can be served from the union after the move completes.

*Evidence:* CASSANDRA-10887: 'node 1 is gaining the range... should be added as a destination for writes and CAS for this range.' Official dynamo.html: 'Write operations are always sent to all replicas, regardless of consistency level. The consistency level simply controls how many responses the coordinator waits for.' transientreplication.html: 'both transient replicas would need to receive any write... so that after the movement takes effect a read quorum is able to return a response.' Trunk StorageService.java exposes getLocalAndPendingRanges -> ClusterMetadata.localWriteRanges, the write-side range computation that combines current+pending. blockFor is raised when pending ranges exist so writes block for the union.

*Sources:* https://issues.apache.org/jira/browse/CASSANDRA-10887, https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html, https://cassandra.apache.org/doc/4.0/cassandra/new/transientreplication.html, https://github.com/apache/cassandra/blob/trunk/src/java/org/apache/cassandra/service/StorageService.java

### 2. [high] Cassandra's CEP-21 (shipped in 5.0) decomposes a node decommission into ORDERED placement steps that guarantee no unserved window: step 1 adds the new owners to the WRITE replica set (leaving node still writing); the leaving node then streams (unbootstraps) its data to the new owners; only after streaming completes does step 2 add the new owners to the READ set while removing the leaving node from reads; step 3 finally removes the leaving node from the WRITE set. So writes go to both current AND pending owners throughout, the read union always covers the range, and the leaving node keeps serving until handoff is durably complete.

*Evidence:* CEP-21 wiki: Step 1 'Assign the nodes taking over the leaving node's ranges as write replicas'; 'Between steps 1 and 2, the leaving node performs unbootstrap, streaming its data to the peers which are taking over those ranges. Only after this is completed can the process move on to step 2.' Step 2 'Assign the nodes taking over the ranges as read replicas, whilst at the same time removing the leaving node from the read replica groups'; Step 3 removes leaving node from write groups. The leaving node stays in read+write sets until streaming finishes; read-set exit (step 2) cannot advance until streaming is done.

*Sources:* https://cwiki.apache.org/confluence/display/CASSANDRA/CEP-21:+Transactional+Cluster+Metadata

### 3. [high] The gossip-convergence-lag ambiguity is a REAL, documented failure of the consistent-hash/gossip model, not a hypothetical. ScyllaDB's pre-Raft coordinator relied on a ring_delay wait (default 30s) for gossip to propagate a topology change before streaming, and writes that begin against the old replica set but finish after ownership shifts can be acknowledged at the requested CL while landing on fewer replicas than CL requires (e.g. an RF=3 QUORUM write ending on just 1 replica). pending_endpoints is the mechanism by which old and new replica sets diverge (when node D joins, A updates pending_endpoints and D replaces A for key K).

*Evidence:* ScyllaDB #5252: 'some acknowledged writes may end up being stored on fewer replicas than the CL of the request requires after a topology change... for RF=3 keyspace a CL=QUORUM write may end up being present on only 1 replica.' 'Node A notices that D joins, updates pending_endpoints, D replaces A for key K.' The coordinator 'waits for ring_delay (default: 30 s) so that the gossip protocol propagates the change of state to all the nodes.' This is precisely the window where different nodes disagree about ownership.

*Sources:* https://github.com/scylladb/scylladb/issues/5252, https://www.scylladb.com/2023/05/09/whats-next-on-scylladbs-path-to-strong-consistency/

### 4. [high] The strong-consistency answer to gossip lag is to replace gossip topology dissemination with a linearized, versioned source of truth and FENCE requests by that version. ScyllaDB moved token/topology metadata from gossip to Raft-replicated, strongly-consistent, linearized state, and signs every read/write with the coordinator's current topology version; a replica with incompatible topology rejects the request and forces a coordinator refresh, eliminating the ambiguous-ownership window. Cassandra's CEP-21 does the analogous thing: an immutable, totally-ordered metadata log with monotonically increasing epochs, where nodes compare epochs on every message to trigger catch-up.

*Evidence:* ScyllaDB blog: 'Token metadata is replicated using Raft... strongly consistent... Token metadata changes are now linearized.' 'Each read or write in ScyllaDB is now signed with the current topology version... If replicas have incompatible topology info, they respond with an error prompting coordinator refresh.' CEP-21: 'Each message any two nodes exchange contains the epoch. Comparing a node's own epoch with the remote node's epoch serves as a mechanism to trigger catch-up' over an immutable totally-ordered log.

*Sources:* https://www.scylladb.com/2023/05/09/whats-next-on-scylladbs-path-to-strong-consistency/, https://cwiki.apache.org/confluence/display/CASSANDRA/CEP-21:+Transactional+Cluster+Metadata

### 5. [high] The per-range-consensus family (CockroachDB, TiKV/PD) avoids any ambiguous-ownership window entirely by routing through a single linearizable leaseholder/leader and changing membership via Raft conf-changes before any role moves. CockroachDB decommissions by having the replicate queue treat the leaving node like a dead replica: UP-replicate the range to a new node first, then DOWN-replicate (remove) from the leaving node - normal replication path, never a special handoff, and the up-then-down ordering preserves availability. TiKV/PD perform a region move as a single ordered Operator of OpSteps: AddLearner/AddPeer (snapshot, tens of seconds) -> TransferLeader (ms) -> RemovePeer (ms); PD also evicts Raft leaders off a restarting/offline store so regions stay available before a new leader is elected.

*Evidence:* Cockroach RFC: replicate queues 'treat decommissioning nodes like dead replicas... up-replicate to a node not in decommissioning state... down-replicate from target nodes.' TiKV scheduling guide: 'Each scheduling Operator is only used to operate a region migration, which including some OpSteps: add peer, transfer the raft group leader and remove peer.' PD best-practices: snapshot steps (AddLearner/AddPeer) 'tens of seconds,' metadata steps (TransferLeader/RemovePeer/PromoteLearner) 'milliseconds.' TiKV #10602: 'When restart/offline a TiKV instance, PD need to evict leader... in case the region is unavailable until the new leader elected.'

*Sources:* https://github.com/cockroachdb/cockroach/blob/master/docs/RFCS/20170608_decommission.md, https://docs.pingcap.com/tidb/stable/tidb-scheduling/, https://docs.pingcap.com/tidb/stable/pd-scheduling-best-practices/, https://tikv.github.io/tikv-dev-guide/understanding-tikv/scalability/scheduling.html, https://github.com/tikv/tikv/issues/10602

### 6. [high] In the centrally-orchestrated families, a placement driver (not the data layout) owns the handoff schedule and rate. TiDB/PD implements membership via three Raft commands (AddReplica, RemoveReplica, TransferLeader). A decommissioned TiKV store goes Offline, PD migrates all its Regions to Up stores, and the store reaches Tombstone only when leader_count and region_count hit zero. The migration is throttle-controllable and gated by an explicit feature flag (enable-replace-offline-replica); disabling it stops PD rescheduling off the offline store - proving the handoff is centrally orchestrated, not implicit in placement.

*Evidence:* tidb-scheduling: 'PD implements replica membership changes through... AddReplica, RemoveReplica, and TransferLeader.' Offline store 'moves all its Regions to other Up stores that meet the relocation conditions'; reaches Tombstone when leader_count and region_count are 0. Best-practices: scale-down marks store offline; 'you can limit the speed of the scheduler... or simply set enable-replace-offline-replica = false to temporarily disable it.'

*Sources:* https://docs.pingcap.com/tidb/stable/tidb-scheduling/, https://docs.pingcap.com/tidb/stable/pd-scheduling-best-practices/

### 7. [high] The Dynamo/Riak lineage gives the closest precedent to a consistent-hash + implicit-ownership store, and it distinguishes two handoff types: OWNERSHIP TRANSFER (a vnode no longer belongs on its physical node, e.g. on a join, so the vnode and its data move) versus HINTED HANDOFF (a secondary vnode that temporarily took a primary's responsibility hands it back when the primary recovers). Sloppy quorum + hinted handoff is the availability trick: writes go to fallback replicas during a transition and are replayed to the rightful owner once it returns, so reads/writes succeed throughout.

*Evidence:* riak_core wiki: 'Ownership Transfer: occurs when a vnode is determined to no longer belong to the physical node it is running on (e.g. when a new node joins)... the vnode needs to be moved. Hinted Handoff: occurs when a secondary vnode took the responsibility for a primary vnode but the primary vnode is reachable again.' These are two distinct handoff mechanisms in the consistent-hash ring; riak_core actually defines four (ownership, hinted, repair, resize).

*Sources:* https://github.com/basho/riak_core/wiki/Handoffs

### 8. [high] etcd/Consul (Raft) structurally avoid split ownership through joint consensus: etcd's Raft implements explicit EnterJoint and LeaveJoint primitives - the configuration is first moved into a joint state whose quorum requires a majority of BOTH the old and new configs (overlapping), then transitioned to the final config in a second step. Because no single config change can ever produce two disjoint majorities, there is never a moment where two leaders or two ownership sets can both make progress.

*Evidence:* etcd PR #10889: 'EnterJoint makes the configuration joint and then applies the changes to it, in preparation of the caller returning later and transitioning out of the joint config into the final desired configuration via LeaveJoint().' EnterJoint transitions e.g. (1 2 3) to (1 2 3)&&(1 2 3) where the incoming+outgoing majorities overlap, preventing any split-brain ownership during the change.

*Sources:* https://github.com/etcd-io/etcd/pull/10889

### 9. [medium] RECOMMENDATION for a consistent-hash + object-storage + gossip R=2 store: adopt Cassandra-style PENDING RANGES as the routing-level fix, in preference to per-position forwarding or adding per-range consensus. Dual-write to current+pending owners and read from their union during a transition, gated so the leaving node stays in both the read and write sets until the new owner has MOUNTED the shared bytes. This directly satisfies (a) leaving-node-keeps-serving-until-handoff-completes (it is in the union until mount confirms) and (b) the gossip-lag ambiguity (the union is a superset of every node's possibly-disagreeing view, so any single-node ownership opinion still routes to a node that serves). Shared object storage makes the otherwise-expensive 'streaming' step a near-instant zero-copy mount, so the pending window is short. Per-position forwarding (new owner proxies to old owner) is a viable smaller variant but adds a request-path hop and a liveness dependency on the old node; full per-range consensus is the most robust but the largest, most invasive change (it abandons the implicit-ownership design the architecture is built on).

*Evidence:* Synthesis/engineering judgment grounded in the confirmed mechanisms: pending-ranges dual-write + union-read is exactly how Cassandra/ScyllaDB hold availability under gossip-driven moves; CEP-21's ordered placement (write-set-first, read-transition-after-streaming, write-set-removed-last) is the gate ensuring the leaving node never exits before handoff. The union-read property is what tolerates per-node ownership disagreement during gossip lag. The zero-copy-mount observation follows from the architecture's shared object storage replacing Cassandra's byte-streaming. This recommendation is an inference from the verified primary mechanisms, hence medium confidence rather than a directly-sourced fact about THIS architecture.

*Sources:* https://cassandra.apache.org/doc/4.0/cassandra/new/transientreplication.html, https://cwiki.apache.org/confluence/display/CASSANDRA/CEP-21:+Transactional+Cluster+Metadata, https://github.com/scylladb/scylladb/issues/5252, https://github.com/basho/riak_core/wiki/Handoffs

## Open questions (the gaps to resolve for shale)

- With R=2 (only two replicas) and union-read during a transition, the temporary replica set spans 3 nodes (old + both new owners or old + new); does the dual-write CL need to rise to ALL-3 transiently as Cassandra's blockFor does, and does that transient durability/availability tradeoff defeat the point for an R=2 store where one slow node already halves availability?
- How is 'the new owner has MOUNTED the shared bytes' confirmed to the coordinator/routing layer in an implicit-gossip model with no per-range consensus? CEP-21 and ScyllaDB use a linearized epoch/version as the gate; without one, what authoritative signal advances the leaving node out of the read set, and can that signal itself race?
- For per-position forwarding (new owner proxies to old owner), how is the forwarding torn down race-free once mount completes, and does it reintroduce the same gossip-lag ambiguity at the proxy-vs-direct decision point?
- Does object storage's CAS/conditional-write capability (the same If-None-Match fencing the slatedb metadata layer uses) offer a cheaper alternative to topology versioning - i.e. fence ownership at the object-store layer per key/range rather than at the routing layer - and would that be smaller than pending ranges?
